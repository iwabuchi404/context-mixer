# UIプラン B: Vue(ハイブリッド)案

UX要件(共通前提):

| 要件 | 値 |
| --- | --- |
| デバイス | PC : モバイル = 5 : 5 |
| 利用比率 | **読み 7 : 書き 3**(読みが主、書きは短い追記が中心) |
| 機能量 | 少なくてよい |
| 最優先 | **読み画面の品質**と**表示スピード** |

## 設計方針: シンプルに保つ(重要)

データ量は個人ナレッジベースの規模(コレクション数十・ドキュメント数百)を超えない。よって本案では**やらないこと**を先に決める:

- ❌ 状態管理ライブラリ(Pinia等) — リアクティブなplain objectで足りる
- ❌ Vue Router / フルSPA — ページは素のMPA、**読みビューだけ**SPA的に動かす
- ❌ Service Worker / オフライン対応 — 複雑さに見合わない
- ❌ 仮想スクロール — 数百件なら素のv-forで一切問題ない
- ❌ SWRフレームワーク — 素朴な `Map` キャッシュで十分
- ⭕ ビルドはVite最小構成のみ(現CDN方式の「Vue全体+未圧縮」をやめて初回を軽くする目的に限定)

---

## コンセプト:「読みビューだけアプリ、残りはただのページ」

構成は**ハイブリッド**。メインの読みビュー(ツリー+本文)を1つのVueアプリにし、ドキュメント間の移動はツリーを保持したまま本文データだけ差し替える(history.pushStateでURLも同期)。検索・キー管理・inboxは今までどおり独立した素のページでよい。

```
体感の流れ:
初回:   起動 → [小さなJS読込 + meta API] → ツリーと本文表示
回遊:   ツリーをクリック → [キャッシュ or 1 API] → 本文だけ即差し替え
2度目に開くdoc → キャッシュから0msで表示、裏で最新を取得
```

## 画面構成

### 1. メイン画面 = ツリー + 本文(読み7割の主戦場・唯一のVueアプリ)

起動時は**前回読んでいたドキュメントを復元**(localStorage)。

```
[PC]                                      [モバイル]
┌────────┬───────────────┬──────┐  ┌──────────────────┐
│ ツリー    │  本文(レンダリング済) │ 目次   │  │ ☰ パンくず > 設計メモ   │
│ ▾ projects│                     │ ・概要  │  │──────────────────│
│   ▾ elbow │  # 設計メモ          │ ・方針  │  │  # 設計メモ           │
│     ・設計 │  本文テキスト…        │ ・課題  │  │  (本文)              │
│   ▸ 日報  │                     │       │  │ [目次▾] ←折りたたみ    │
│ ▸ refs   │                     │       │  │                     │
└────────┴───────────────┴──────┘  └──────────────────┘
                                          ☰ タップでツリーがドロワーで出る
```

### 2. 検索

- 素のページでもVueアプリ内のオーバーレイでもよいが、**アプリ内オーバーレイ(⌘K / 検索アイコン)を推奨** — 読みの文脈を離れずに次のdocへ飛べるのは読み7割と相性が良い
- 入力即時(debounce 300ms)、ヒット語ハイライト、結果タップで本文差し替え

### 3. クイックキャプチャ(書き3割)

- 本文末尾に常設の「+ 追記」ボックス(モバイルは下部固定ボタン→展開)
- **楽観的更新はここだけに使う**: 「追記する」を押した瞬間に本文末尾へ反映し、裏でappend APIを送る。失敗時はテキストを保持してリトライ表示(書いた内容を失わせない)
- 下書きはlocalStorageに自動保存(これは1行で書ける範囲の「ついで」機能)

### 4. 編集

- 「編集」ボタンで本文領域がエディタに切り替わる(PC: 左textarea/右ライブプレビューの分割、モバイル: タブ切替)
- ライブプレビューはVue案の素直な強み(同一データを2つの表示にバインドするだけ)
- 保存(PUT)後はレンダリング表示へ戻る

### 5. 管理(APIキー・inbox承認)

- 既存 keys.html を流用。素のページのまま。inbox承認一覧を追加し、ヘッダにバッジ表示

## 読みUIの工夫

(タイポグラフィ・約物・コード・表の扱いはHTMX案§読みUIと同一仕様。以下はVueならではの点)

- **目次の現在地ハイライト**: IntersectionObserverで連動。目次クリックでスムーズスクロール
- **`[[doc_xxx]]` のホバープレビュー**: リンク先がキャッシュ済みなら**即時**ミニカード表示(タイトル+冒頭)。未取得ならmeta APIを裏で取得。モバイルは長押し
- **バックリンクを本文末に「次に読む」導線として常設**
- **前後ナビ**(同コレクション内の前/次)
- **読み位置・開いていたdocの復元**(localStorage)
- **ツリー→本文のプリフェッチ**: ツリーに見えているdocのmeta(目次まで)をアイドル時間に先読み → クリック時は本文fetchだけ、体感ほぼ0
- Markdownレンダリングはクライアント(marked + DOMPurify)。データが小さいので速度問題にはならない

## ツリーUIと実装上の工夫

**UI仕様はHTMX案と共通**(PC左ペイン・モバイルドロワー・現在地強調とパス自動展開・priority固定表示・タイトル絞り込み)。Vue案での実装方針:

- **ツリーデータは起動時に一括取得して終わり**: `/collections`(ツリー構造で返る)+ `/docs?collection=`数回でメモリに展開。個人KBの規模なら合計数十KB。遅延ロードや差分同期は**作らない**(オーバーエンジニアリング回避)
- 展開状態・スクロール位置はVueの状態としてそのまま保持される(SPA領域なので何も工夫がいらない — これがハイブリッド構成の利点)
- タイトル絞り込みはメモリ内filter(computed)で即時
- 追記・作成・削除後は該当コレクションのリストだけ再取得(全体リロードしない)

## デザイン的な方向性

**「静かな書斎」— HTMX案と同一の見た目を共有する**(案の選択でデザインが変わるべきではない)

- 生成り寄りの白地+墨色テキスト、アクセント藍系1色、ダークモードOS追従
- システムフォントのみ(Webフォント配信なし)、罫線と余白で構成、カード・影なし
- アイコンは線画(Lucide)最小限
- Vue案特有の注意: **ローディングを「デザイン」しない**。スケルトンやスピナーを飾る前にキャッシュ表示で消す。出すのは「裏で更新中」を示す小さなインジケータ1つだけ

## 表示スピード戦略

| 施策 | 効果 |
| --- | --- |
| Vite最小ビルド(Vue + marked で~60KB gz目安) | 初回JSを現CDN方式の1/3以下に |
| 起動時ツリー一括取得+docキャッシュ(Map) | 回遊は0〜1リクエスト |
| 既読docはキャッシュ即表示→裏で更新 | 「戻る」「再訪」が0ms |
| ツリー可視docのアイドル先読み | クリック時の待ちを消す |
| clerk-jsの遅延初期化 | 認証チェックで描画をブロックしない |

**正直な注意点**: 初回アクセス・ハードリロードはHTMX案より遅い(目標~1秒)。「2回目以降と回遊の滑らかさ」で勝負する案。

## 段階リリース

1. **P1: メイン画面(ツリー+本文+読みUI一式、Vite化)** ← 価値の8割
2. P2: ⌘K検索オーバーレイ + クイックキャプチャ(楽観的更新) + 編集ライブプレビュー
3. P3: inbox承認 + 画像貼り付け(エディタにドロップ→files API→URL挿入)

## この案の弱点(正直に)

- 初回表示はHTMX案に構造的に勝てない
- キャッシュ・楽観的更新の「外れた時」(競合・失敗)のフォローを雑にすると信頼性が崩れる — ただし本案はその適用範囲をappendと既読キャッシュに限定して被害を小さくしている
- Markdownレンダリング・サニタイズがクライアント依存(DOMPurify必須)

## この案を選ぶ理由があるとすれば

- ライブプレビュー編集・ホバープレビューの即時性など、**画面内の応答性**を重視する場合
- 既存Vue資産と慣れを活かし、サーバー側テンプレートを持ちたくない場合
