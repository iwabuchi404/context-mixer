# UIプラン A: HTMX(サーバーレンダリング)案

UX要件(共通前提):

| 要件 | 値 |
| --- | --- |
| デバイス | PC : モバイル = 5 : 5 |
| 利用比率 | **読み 7 : 書き 3**(読みが主、書きは短い追記が中心) |
| 機能量 | 少なくてよい |
| 最優先 | **読み画面の品質**と**表示スピード** |

---

## コンセプト:「紙のように速く開き、そのまま読み耽れる」

読みが7割なら、UIの主役は「読書画面」そのもの。HTMX案の本質は **読み画面を「ただのHTML」にすること**。Markdownのレンダリングをエッジ(Hono)側で行い、ブラウザにはスタイル済みHTMLだけが届く。JSのロード・実行・API呼び出しを待たずに本文が表示される。

```
体感の流れ(モバイル回線でも):
タップ → [エッジでSSR 数十ms] → 本文が即表示
        (JSロード待ちなし・スピナーなし・レイアウトシフトなし)
```

なお「100% MPA」にはこだわらない。後述のとおり、**ツリーを保持したまま本文だけを差し替える**部分置換(hx-get + hx-push-url)を使うので、読み回遊の操作感は実質SPAになる。

## 画面構成

### 1. メイン画面 = ツリー + 本文(読み7割の主戦場)

アプリを開くと**前回読んでいたドキュメントが開いた状態**で復元される(Cookieに最後のdoc記録)。「開く→続きを読む」がゼロ操作。

```
[PC]                                      [モバイル]
┌────────┬───────────────┬──────┐  ┌──────────────────┐
│ ツリー    │  本文(レンダリング済) │ 目次   │  │ ☰ パンくず > 設計メモ   │
│ ▾ projects│                     │ ・概要  │  │──────────────────│
│   ▾ elbow │  # 設計メモ          │ ・方針  │  │  # 設計メモ           │
│     ・設計 │                     │ ・課題  │  │  (本文)              │
│     ・調査 │  本文テキスト…        │       │  │                     │
│   ▸ 日報  │                     │       │  │ [目次▾] ←折りたたみ    │
│ ▸ refs   │                     │       │  │                     │
└────────┴───────────────┴──────┘  └──────────────────┘
                                          ☰ タップでツリーがドロワーで出る
```

### 2. 検索(読みの入口その2)

- 入力欄に打つとインクリメンタルに結果が差し替わる(hx-trigger="keyup delay:300ms")
- 結果はヒット語ハイライト付きスニペット。タップで該当セクションへ直接ジャンプ

### 3. クイックキャプチャ(書き3割)

- メイン画面の本文末尾に常設の「+ 追記」ボックス(モバイルは下部固定ボタン→展開)
- 読んでいるドキュメントにそのまま追記できる=「読んでいて思いついたら書く」動線
- 別ドキュメントへの追記はツリーから宛先を選ぶだけ。送信は append API、完了後は本文の該当部分だけ部分置換で更新される

### 4. 管理(APIキー・inbox承認)

- 表+フォームの素直なCRUD画面。UX投資はしない
- inbox承認はヘッダに未承認バッジ、一覧から1タップで承認/却下

## 読みUIの工夫

- **タイポグラフィ**: 本文最大幅65字相当・行間1.8・モバイル16px以上。日本語長文前提で約物まわりの調整(`text-spacing-trim`)
- **目次の現在地ハイライト**: スクロールに連動して目次の現在セクションが点灯(IntersectionObserverの数行だけのJS)
- **`[[doc_xxx]]` はタイトルに解決して表示**(SSRなので確実)。PCはホバーで概要ポップオーバー、モバイルは長押しでミニカード
- **バックリンクを「脚注」として本文末に常設**: 「このページを参照しているページ」が読み終わりに自然に目に入る=次に読むものへの導線
- **前後ナビ**: 本文末に「同じコレクションの前/次のドキュメント」。連続読みを途切れさせない
- **見出しアンカー**: 見出しホバーで#リンクコピー(共有・引用用)
- **コードブロック**: サーバー側でシンタックスハイライト(JS不要)+コピーボタン。長いブロックは折りたたみ
- **表は横スクロールコンテナで包む**(モバイルでレイアウト崩壊させない)
- **読み位置の復元**: ドキュメントごとにスクロール位置を記憶
- **セクション編集はその場で**: 各見出し横の「✎」でそのセクションだけがフォームに変わる(hx-get)。読みの文脈を離れずに直せる

## ツリーUIと実装上の工夫

ツリーは読み体験の「もう半分」。以下を仕様とする。

**UI**
- PC: 左ペイン固定(幅リサイズ可・⌘\\で開閉)。コレクション>ドキュメント(親子)の2階層構造をそのまま表示
- モバイル: ハンバーガー→左ドロワー。現在のドキュメントの位置まで自動スクロール
- 現在表示中のdocを強調し、**そこまでのパスを自動展開**(迷子にならない)
- 各コレクションは更新日時順 or 名前順をトグル。priority=highのdocは上部に固定+小さなマーク
- ツリー内インクリメンタル絞り込み(タイトルのfilter。検索APIとは別物の軽い機能)

**実装上の工夫**
- **初期SSRは「現在docへのパスだけ展開した状態」で出力**。全ツリーを毎回描かない
- ノード展開時に `hx-get /tree/:id` で**子要素のHTML断片だけ遅延取得**。documentsの `path` カラム(LIKE検索)があるので1クエリで取れる — スキーマがこのUIをそのまま支える
- 展開状態はlocalStorageに記憶し、次回SSR時にCookie経由で反映
- **本文遷移時にツリーを再描画しない**: ツリーのリンクは `hx-get`(本文領域のみtarget)+ `hx-push-url`。ツリーのDOMは保持されるためスクロール位置・展開状態が維持される。ここが「100% MPAではない」部分で、読み回遊は実質SPAの操作感になる

## デザイン的な方向性

**「静かな書斎」— コンテンツが主役、UIは消える**

- 配色: 生成り寄りの白地(#FAFAF8系)+墨色テキスト。アクセントは1色(藍系)のみ、リンクと現在地表示にだけ使う
- ダークモードはOS追従(読み物アプリとして夜間利用を想定)
- 字体: 本文=システムフォント(Hiragino/Noto Sans JP)、コード=等幅。**フォント配信はしない**(速度最優先と矛盾するため)
- 装飾は罫線と余白で構成。カード・影・グラデーションは使わない
- アイコンは線画(Lucide)を最小限。ラベル優先
- モーション: View Transitionsのクロスフェード150ms程度のみ。「動き」より「即応」をデザインのアイデンティティにする

## 表示スピード戦略(この案の核)

| 施策 | 効果 |
| --- | --- |
| エッジSSR(Hono JSX) | 初回表示にJS実行が不要。TTFB=エッジ応答のみ |
| 本文のみ部分置換(ツリー保持) | 回遊時の転送量・描画コストが最小 |
| preload拡張(hover/touchstartで先読み) | 体感ゼロ遷移 |
| CSS 1ファイル+htmx 14KBのみ | 低速回線でも初回から速い |
| Cache-Control + ETag | 再訪・戻る操作が即時 |

## 認証の扱い(UXに関わる点のみ)

セッションはCookieベースに統一する(SSRと相性が良い)。一度ログインすれば、どのURLを直接開いても即表示=ブックマーク・共有URLが自然に機能する。

## 段階リリース

1. **P1: メイン画面(ツリー+本文SSR+読みUI一式)** ← 価値の8割
2. P2: インクリメンタル検索 + セクションその場編集 + クイックキャプチャ
3. P3: inbox承認・画像アップロード・PWA化(ホーム画面追加)

## この案の弱点(正直に)

- 同一画面内のリッチな双方向UI(ライブプレビュー等)は苦手 — セクション単位編集で回避する設計
- 現Vue製3ページは作り直し
- UI修正=サーバーデプロイが必要
